# Product Matching

Match marketplace product listings using only the text sellers type in. Given ~26k listings in Portuguese, this project:

- **(a)** gives the **probability that two listings are the same product**;
- **(b)** reads **type, category, brand, color and model** from a product name, and answers `None` when it isn't sure;
- **(c)** returns the **most relevant listings for a short search** such as *notebook sony 4 GB*.

It started as a 2022 data-science take-home ([`legacy/challenge_v1.ipynb`](legacy/challenge_v1.ipynb), kept unchanged). The 2022 version built reasonable pieces but never measured them. This version adds an answer key (listing pairs, names and search judgments, labelled by an AI assistant (Claude) using the written rules below; not yet reviewed by a person), evaluates everything on held-out data next to the 2022 approach, and packages the result as a small API.

For a plain-language walkthrough of the decisions and results, see [`notebooks/analysis.ipynb`](notebooks/analysis.ipynb).

### (c) Search

## How it works

| | Approach | Key choices |
|---|---|---|
| Text cleanup | lowercase, strip accents, repair broken encoding, unify units and model codes | `4 GB`, `4gb` and `4096 MB` all become `4gb`; `MSS-18CR` becomes `mss18cr` |
| (a) Matching | candidate generation (shared model code ∪ top-10 character n-gram neighbours ∪ top-10 embedding neighbours), then a logistic regression on 14 pairwise features | features include rarity of a shared code and capacity / voltage / color conflicts; regularization, calibration and threshold chosen by cross-validation on training pairs |
| (b) Extraction | type & category: linear classifier on word + character TF-IDF; brand: brand dictionary, then classifier; color: color words; model: ranked code-like tokens | the model abstains below a confidence set on a validation split (target precision 0.95; 0.90 for model) |
| (c) Search | BM25, character n-grams, `intfloat/multilingual-e5-small` embeddings, and a reciprocal-rank-fusion hybrid of BM25 + embeddings | fusion constant k = 60 (standard, not tuned on the judged queries) |

**Ground truth** (all editable CSVs in [`labels/`](labels/)). Every label was produced by an AI assistant (Claude) applying the rule below; none has yet been reviewed by a person.

| File | Contents |
|---|---|
| `pairs.csv` | 800 listing pairs labelled same / different: 350 that share a model code, 300 near-lookalikes, 150 random same-type pairs. Split 500 train / 300 test, grouped so near-copies stay on one side. |
| `extraction_check.csv` | 200 held-out names with the color and model actually stated in the name (empty = None). |
| `queries.csv`, `judgments.csv` | 30 queries and 1,237 graded results (pooled from every system's top 10 plus pattern matches). |

"Same product" means the same manufacturer model with no conflicting variant (color, voltage, capacity, size) where both listings state one. A detail stated on one side only is not a conflict. Hard cases are flagged in an `unsure` column with a note.

### Human review of the labels

`pm review-sample` writes `labels/review_pairs.csv`: every pair flagged `unsure` plus 100 random test pairs, with an empty `my_label` column and without the AI's label (the review is blind). After filling `my_label` with 1 (same) or 0 (different), `pm review-agreement` reports agreement with the AI labels (overall, on the `unsure` pairs, on the test pairs, and Cohen's kappa), lists the disagreeing pairs, writes `reports/review.json` and updates this section.

## Run it locally

Requires Python 3.12.

```bash
make install          # .venv + pinned requirements (requirements.txt, requirements-dev.txt)
make evaluate         # ~5 min: scores baseline vs new on held-out data -> reports/, updates this README
make build            # ~7 min: fits everything on all data -> artifacts/service.joblib (44 MB, not committed)
make serve            # API on http://127.0.0.1:8000  (interactive docs at /docs)
make test             # unit, API contract and end-to-end tests (make test-fast skips the ~1 min e2e test)
```

The CLI behind these targets is `pm` (`pm sample-labels`, `pm pool-queries`, `pm build`, `pm evaluate`, `pm serve`). Seeds are fixed (`SEED = 42`). The first run downloads the embedding model (~470 MB) from Hugging Face.

## Run it in Docker

```bash
docker build -t product-matching .     # builds the models inside the image
docker run --rm -p 8000:8000 product-matching
```

The image installs the CPU-only PyTorch wheel and fits all models at build time from the CSV and labels, so it needs no other files.

## API

**`POST /match`**: probability that two listings are the same product. `marca` (brand) is optional.

```bash
curl -s localhost:8000/match -H 'content-type: application/json' -d '{
  "a": {"nome": "Refrigerador Consul CRM33 263 Litros Inox"},
  "b": {"nome": "Refrigerador Frost Free 2 Portas CRM33 249L Inox 220v - Consul"}}'
```
```json
{"probability": 0.901, "same_product": true, "threshold": 0.337}
```

**`POST /extract`**: fields read from a name; `value` is `null` when the system is not confident enough.

```bash
curl -s localhost:8000/extract -H 'content-type: application/json' \
  -d '{"nome": "Notebook Sony Vaio VPC-EG13EB/L Intel Core i3 4GB 500GB Azul"}'
```

## Limitations

- **Small answer key.** 52 held-out duplicate pairs and 30 queries. Confidence intervals are wide (see the brackets above); differences inside them are ties. BM25 and the hybrid search are statistically indistinguishable here.
- **The labels are AI-generated and unreviewed.** Every label was produced by an AI assistant (Claude) applying the written rules, and no person has checked them yet, so the metrics measure agreement with those labels. See *Human review of the labels* for the review workflow.
- **Test pairs over-represent hard cases** (shared codes and lookalikes), so precision over all candidate pairs in the catalogue would differ. Only 5 of 139 labelled duplicates lack a shared model code, so the model has little evidence for that case, and candidate-generation recall is measured mostly on pairs it was designed to find.
- **Type, category and brand are scored against seller-entered labels**, which have their own errors.
- **The model extractor rarely abstains.** Its threshold was tuned on names that all contain a model, so it only says None when no code-like token exists (precision 0.82 against a 0.90 target on the 200 checked names).
- **Search ignores product type.** For *notebook sony 4 GB* the top hit is a Sony 4 GB memory stick. The 2022 baseline, which adds a predicted type and brand to the query, still wins on 3 of 30 queries for this reason. Using the query's predicted type and brand (part b) to boost results is the obvious next step.
- **Pooled judgments.** A listing that no evaluated system retrieved is treated as irrelevant.
- **8 of 262 names with broken encoding** could not be repaired automatically.
- **The Docker image is large (4.7 GB)**, mostly PyTorch and the embedding model. Exporting the encoder to ONNX would shrink it substantially.

## The challenge

*Translated from the original Portuguese.*

### Context

One of the biggest challenges for marketplace e-commerce platforms is comparing product information based on text descriptions. Each seller registered on the platform can enter product data in very different ways, sometimes with incomplete information, and even the most basic description, the name shown on the product page, is not standardized.

Grouping identical products matters for everything from pricing strategy and sales forecasting to search and recommendation. Duplicate products in the catalog also make inventory management harder and marketing strategies less efficient.

### Problem

Magazine Luiza, one of the largest retailers in Brazil, has a large product catalog, much of it coming from external sellers on its marketplace. The sample in the CSV file contains some of the information sellers provided when registering each product: the product's **name**, **type**, **category**, **brand**, **color** and **model**. The file is tab-separated (`\t`), and fields that were not filled in contain the word `None`.

Build a matching solution using the data provided. The solution should answer the following questions:

1. **(a)** Given two products, what is the probability that they are the same product?
2. **(b)** Given a product name, how can the type, category, brand, color and model be recovered? If the product does not have a piece of information, the system should return `None`.
3. **(c)** How can the matching solution be used to return the most relevant products for a customer's simple search on the website? Example search: *notebook sony 4 GB*.
   Note: adapt the matching solution you built to solve this item; there is no need to build a system or an API.

### Evaluation criteria

- Understanding of the problem and solution design.
- Knowledge of natural language processing and machine learning models.
- Ability to explain complex ideas simply, that is, to communicate with people who don't share the same academic background or understanding of technology.
